# Режим `policy` для harbor-scanner-grype

Дата: 2026-09-25. Статус: устройство согласовано в обсуждении, документ ждёт проверки.

## 1. Зачем

Сейчас коннектор выставляет уровень по формуле EPSS × 100 × CVSS/10 с порогами 85/70/50/0.01. На выгрузке
реестра (16 649 уникальных уязвимостей) это дало 16 533 Low. Коннектор не учитывает каталог KEV, а бюллетени
Amazon Linux (ALAS) и Oracle Linux (ELSA) всегда получают Low: для них не находится EPSS и подставляется 10%.

Нужен режим, который:

- не пропускает то, что атакуют или вот-вот начнут: KEV, высокий EPSS, вредоносные пакеты, публичные эксплойты;
- не заваливает Critical: на выгрузке ожидается около 65 Critical и около 270 High;
- пишет в Harbor, почему уязвимость получила свой уровень.

## 2. Основа и паритет с работающим образом (этап 0)

Код берём из github.com/ant1freeze/harbor-scanner-grype, ветка main, коммит f3f2b9d8. Работающий образ из
комплекта (`ant1freeze/harbor-scanner-grype:latest`) собран из правок, которых в main нет:

| Что | В main | В образе из комплекта |
|---|---|---|
| grype / syft / Alpine | 0.100.0 / 1.5.0 / 3.19 | 0.117.0 / 1.51.1 / 3.24.1 |
| Сборка | Dockerfile копирует готовый бинарник `scanner-grype-linux` из репозитория | собран из исходников, которых нет в репозитории |
| Настройки уровня | файл `risk-config.yaml` | переменные `SCANNER_RISK_*` |
| Доступ к реестру | TLS-проверка всегда выключена | `SCANNER_REGISTRY_HOST_MAP`, `SCANNER_EXTRA_HOSTS`, `SCANNER_REGISTRY_INSECURE_USE_HTTP`, `SCANNER_REGISTRY_INSECURE_SKIP_TLS_VERIFY`, `SCANNER_REGISTRY_USERNAME/PASSWORD` |
| Логи | `SCANNER_LOG_LEVEL` | плюс `SCANNER_LOG_FORMAT` (text/json) |
| Обновление базы | cron `0 0 * * *` зашит в образ | `GRYPE_DB_UPDATE_SCHEDULE`, `TZ`, `GRYPE_DB_MAX_ALLOWED_BUILT_AGE`; сканы базу не качают |
| Очередь | — | прерванные задания возвращаются в очередь при старте |

**Решение команды: восстанавливаем недостающее поверх main (вариант Б).** Исходников образа нет, поэтому
образцом служит сам образ из комплекта (`harbor-scanner-grype-amd64.tar.gz`):

- его скрипты `start.sh` и `update-grype-db.sh` — они переносятся как есть;
- список переменных и их значения по умолчанию, извлечённые из бинарника;
- имена функций из таблицы символов бинарника;
- комментарии в `env.example`, `docker-compose.yml` и `INSTALL.md`.

Где точное поведение бинарника неизвестно, обязательным считается поведение, описанное ниже.

### 2.1 Сборка

- Двухэтапный Dockerfile.
  - Сборка: golang 1.22, `CGO_ENABLED=0`.
  - Работа: Alpine 3.24.1, пакеты `ca-certificates curl su-exec tzdata`.
  - grype 0.117.0 и syft 1.51.1 скачиваются с GitHub Releases с проверкой контрольных сумм, как в образе из
    комплекта.
- Пользователь `scanner` (uid 10000), каталоги `/home/scanner/.cache/{grype,reports}` и
  `/var/log/grype-update.log`.
- База уязвимостей вшивается при сборке: `grype db import`, если в контексте сборки есть `grype-db.tar.zst`,
  иначе `grype db update`.
- Окружение: `GRYPE_DB_AUTO_UPDATE=false`, `GRYPE_CHECK_FOR_APP_UPDATE=false`,
  `SYFT_CHECK_FOR_APP_UPDATE=false`, `GRYPE_DB_CACHE_DIR=/home/scanner/.cache/grype`.
- Точка входа — `start.sh`, порт 8090.
- Готовый бинарник `scanner-grype-linux` удаляется из репозитория.

### 2.2 Скрипты

`start.sh` и `update-grype-db.sh` берутся из образа как есть:

- записи `SCANNER_EXTRA_HOSTS` добавляются в `/etc/hosts`;
- cron обновляет базу по `GRYPE_DB_UPDATE_SCHEDULE` с учётом `TZ` от имени `scanner`;
- журнал обновления уходит в лог контейнера;
- сам коннектор запускается через `su-exec scanner`.

К ним добавляется работа с Exploit-DB (раздел 7).

### 2.3 Настройки, которых нет в main

### 2.4 Доступ к реестру

- **Подмена адреса.** `SCANNER_REGISTRY_HOST_MAP` — пары `host=target` через запятую. Если хост реестра из
  запроса Harbor совпадает с `host` (без учёта регистра, порт не сравнивается), коннектор ходит на `target`.
  `target` без порта сохраняет порт из запроса. Работает и для сканов, и для SBOM.
- **HTTP и TLS.** Режим берётся из `SCANNER_REGISTRY_INSECURE_*`, а не выключается всегда, как в main.

### 2.5 Очередь

- **Надёжная очередь.** Задания кладутся в список Redis, а не в Pub/Sub. Воркер атомарно переносит задание в
  список «в работе» и убирает его оттуда по завершении.
- **Возврат после остановки.** При старте всё, что осталось в «в работе», возвращается в очередь, в лог
  пишется «Requeued interrupted scan jobs».
- **Отметка ожидания.** При приёме задания и при каждом опросе отчёта Harbor ставится отметка «Harbor ждёт» со
  сроком `SCANNER_HARBOR_POLL_TIMEOUT`. Перед запуском воркер её проверяет. Если отметка истекла, то есть
  Harbor перестал ждать, скан пропускается: задание получает статус Failed с причиной, в лог пишется
  «Scan skipped».
- **Сроки хранения.** Задание в очереди живёт `SCANNER_STORE_REDIS_PENDING_JOB_TTL`, готовый отчёт —
  `SCANNER_STORE_REDIS_SCAN_JOB_TTL` (1h).
- **Остановка.** По SIGTERM воркеры не берут новые задания и дожидаются идущих сканов, пока контейнер даёт
  время. Недоделанные остаются в «в работе» и вернутся в очередь при следующем старте.
- **Временные файлы.** У каждого скана свой каталог внутри `SCANNER_GRYPE_TMP_DIR`, он передаётся grype и syft
  как `TMPDIR`. При старте остатки прошлых сканов удаляются.
- **Таймаут.** grype и syft останавливаются через `SCANNER_GRYPE_TIMEOUT`, задание получает Failed «scan timed
  out».

### 2.6 Логи и метаданные

- **Формат** — по `SCANNER_LOG_FORMAT`.
- **События сканов:** «Scan queued», «Scan started», «Scan finished» (длительность, число находок по уровням),
  «Scan failed» (причина), «Scan skipped» (причина), а также число свободных воркеров. Учётные данные в логи
  не попадают (раздел 8).
- **При старте** в лог пишутся дата сборки базы grype по `grype db status` и дата файла Exploit-DB.
- **Метаданные.** `/api/v1/metadata` отдаёт дату сборки базы в свойстве
  `harbor.scanner-adapter/vulnerability-database-updated-at`, Harbor показывает его в списке сканеров.

## 3. Устройство

### 3.1 Компоненты

- **`pkg/policy`** — пять правил. Одна функция без сети и диска: на вход находка grype, индекс Exploit-DB,
  пороги и дата оценки; на выход уровень, пояснение и ссылки на эксплойты: страницы Exploit-DB (не больше
  пяти), а если номеров Exploit-DB нет, — ссылка на PoC, которую называет пояснение.
- **`pkg/exploitdb`** — индекс «CVE → номера Exploit-DB» из `files_exploits.csv`. Файл перечитывается, когда
  меняется, проверка не чаще раза в минуту. Если файл пропал, не читается или сломан, остаётся список,
  загруженный раньше, а если его не было — индекс пустой; в лог пишется предупреждение.
- **`pkg/grype`, модель** — добавить поля, которые сейчас выбрасываются: `risk`, `knownExploited`
  (`cve`, `dateAdded`, `knownRansomwareCampaignUse`), `cwes` (`cve`, `cwe`), а у `relatedVulnerabilities` —
  `cvss` и `urls`.
- **`pkg/scan/transformer`** — режим `policy`:
  - одна строка отчёта на каждую находку grype, то есть пару «уязвимость + пакет»;
  - описание = пояснение + « — » + описание из базы;
  - ссылки = ссылки из базы + ссылки на эксплойты из `pkg/policy`, без повторов (ссылки Exploit-DB
    сравниваются по номеру, в любой форме адреса).
- **`pkg/etc`** — новые настройки (раздел 6).

Попутно исправляется ошибка сборки отчёта. Сейчас для каждой уязвимости берётся пакет первой находки с тем же
ID. Если CVE есть в нескольких пакетах образа (libcrypto3, libssl3, openssl), все её строки получают первый пакет,
а остальные пакеты теряются. Новый цикл идёт по находкам, а не по уязвимостям.

### 3.2 Поток данных

Harbor → `POST /api/v1/scan` с ключом → очередь в Redis → `grype -o json` → для каждой находки
`policy.Evaluate` → отчёт Harbor → `GET /api/v1/scan/{id}/report`.

## 4. Правила

### 4.1 Что берётся из JSON grype

- `vulnerability`: `id`, `severity`, `description`, `urls`, `cvss` (`version`, `vector`, `metrics.baseScore`),
  `epss` (`cve`, `epss`), `knownExploited`, `cwes`, `risk`.
- `relatedVulnerabilities`: `id`, `cvss`, `urls`.
- CVE находки: `id` уязвимости и связанных записей, если он начинается с «CVE-», плюс `cve` из `epss`,
  `knownExploited` и `cwes`.

### 4.2 Порядок

Правила 1 и 2 ставят уровень окончательно. Иначе уровень даёт правило 3 или 4, затем его может поднять правило 5.

1. **KEV.** `knownExploited` не пуст → Critical.
2. **Вредоносный код.** Любое из четырёх → Critical:
   - описание начинается с одной из формулировок бюллетеня GitHub о вредоносном пакете: «Malware in »,
     «Malicious code in », «Malicious Package in », «Embedded Malicious Code in », «Embedded malware in »;
   - описание — формулировка RustSec о крейте, удалённом за вредоносный код: в нём есть и «removed from
     crates.io», и «malicious code» (в базе 17 таких бюллетеней, все о вредоносных крейтах);
   - находка из бюллетеня GitHub (namespace `github:…`) и её номер есть в списке бюллетеней о вредоносных
     пакетах с нестандартным заголовком (бэкдоры RubyGems 2019 года, event-stream, @solana/web3.js, LiteLLM и
     другие). Список — 62 номера GHSA и 15 их CVE (grype показывает CVE вместо GHSA при
     `SCANNER_GRYPE_BY_CVE=true`), снимок базы grype от 2026-09-15. Проверка только для бюллетеней GitHub
     нужна потому, что записи дистрибутивов grype называет номером CVE: запись Ubuntu о пакете `rails` с той
     же CVE вредоносной не является;
   - среди `cwes` есть CWE-506.

   «Malicious code in <пакет> (<экосистема>)» — это пакеты из OpenSSF malicious-packages, которые GitHub
   перенёс в свою базу (npm, PyPI, RubyGems, NuGet, crates.io, Go, Maven, Packagist); в базе grype таких
   бюллетеней втрое больше, чем «Malware in». Обычные уязвимости со словом Malicious в названии («Malicious PDF
   can inject JavaScript…») под правило не попадают: сравнивается начало описания целиком.
3. **Лесенка по риску**, если есть хотя бы одно значение EPSS.
   - Риск — поле `risk` из grype.
   - Исключение: если EPSS есть по нескольким CVE и максимальный больше первого, риск пересчитывается по
     формуле grype с максимальным EPSS: `min(1, maxEPSS × S) × 100`. Здесь S — множитель критичности grype:
     среднее из «строковая критичность / 10» и «среднее ненулевых базовых оценок CVSS / 10», а без CVSS —
     только строковая критичность. Шкала как в grype: Negligible 0.5, Low 3, Medium 5, High 7.5,
     Critical 9, прочее 5.
   - Пороги: от `SCANNER_POLICY_CRITICAL` (70) — Critical, от `SCANNER_POLICY_HIGH` (30) — High,
     от `SCANNER_POLICY_MEDIUM` (10) — Medium, иначе Low.
   - С порогами сравнивается риск в том виде, как он показан в пояснении и в таблице grype, — с одним
     знаком после точки: 29.96 показывается как 30.0 и даёт High. Риск меньше 0.1 показывается как «<0.1»
     (как у grype) и считается нулём. Так уровень не расходится с текстом.
   - Для записей из KEV пересчёта нет: у них grype не смотрит на EPSS (и до правила 3 они не доходят).
4. **Нет EPSS**, ни одного значения. Берётся критичность grype, но не выше High: Critical → High,
   High → High, Medium → Medium, Low → Low, Negligible → Low, Unknown или пусто → Unknown.
5. **Эксплойт.** Он есть, если по любой CVE находки есть номер в Exploit-DB или среди `urls` уязвимости и
   связанных записей есть ссылка на PoC. Если уровень ниже High:
   - вектор атаки сетевой и критичность grype High или Critical → High. Вектор берётся из CVSS самой записи
     находки (дистрибутива, GitHub); если у неё векторов нет (бюллетени ALAS/ELSA, многие записи Debian — на
     реальных отчётах 156 из 595 находок), — из связанных записей (NVD). Сетевым он считается, если хотя бы один из этих векторов — `AV:N`. Так локальная уязвимость, у
     которой один из векторов NVD сетевой (например, CVE-2025-69720 в ncurses: у Debian `AV:L`, у NVD два
     `AV:L` и один `AV:N`), не поднимается до High «по сети». У RHEL, SUSE, GitHub и Bitnami собственный
     вектор — оценка самого поставщика; у Fedora, Alpine, Debian, Alma и Echo это обычно копия основной оценки
     NVD, и правило предпочитает её вторичным оценкам CNA и CISA ADP (в случае ncurses сетевой вектор был от
     CISA ADP). По всей базе правило снимает около 7 500 устаревших сетевых пометок от оценок CVSS v2;
   - иначе уровень не ниже Medium.

   Если уровень уже High или Critical, эксплойт только упоминается в пояснении.

Ссылкой на PoC считается адрес, подходящий под шаблон из `tools/rescore.py` (без учёта регистра):
`exploit-db\.com|packetstormsecurity\.com/files|rapid7\.com/db/modules|metasploit|0day\.today|seebug\.org|github\.com/[^/]+/[^/]*(poc|exploit|cve-\d{4}-\d+)`,
кроме адресов, в которых эксплойта нет (`notPoCPattern` в `pkg/policy/facts.go`):
- копий бюллетеней производителей на Packet Storm — имя файла начинается с «<Производитель>-Security-Advisory»
  (Notice, Bulletin, Announcement), например `Kernel-Live-Patch-Security-Notice-LSN-0053-1.html`,
  `Slackware-Security-Advisory-curl-Updates.html`, а также `USN-…` и `Security-Notice-For-…`. Бюллетени
  исследователей («Qualys-Security-Advisory-…») остаются: в них есть детали эксплуатации;
- служебных страниц: списков Packet Storm по автору, дате и тегам; главной Exploit-DB, её docs, papers, GHDB,
  страниц автора и поиска.

На базе от 2026-09-15 исключение убирает 146 из 147 копий бюллетеней среди 6 356 ссылок Packet Storm и не
трогает ни одного эксплойта. Без него такие копии давали, по оценке на синтетических находках из базы, 2 859 ложных подъёмов по правилу 5 — в основном
уведомления Ubuntu Kernel Live Patch и бюллетени Slackware, на которые ссылаются CVE ядра во всех
дистрибутивах.

### 4.3 Уровни в Harbor

Critical, High, Medium, Low, Unknown. Уровень отчёта целиком — максимальный по находкам, как сейчас.

## 5. Пояснение

Формат: «<Уровень> на <дата оценки>: <главная причина>; <дополнительные факты>. — <описание из базы>», дата —
день скана в часовом поясе коннектора (`TZ`), например «High на 2026-09-25: …». Дата нужна потому, что Harbor
хранит описание находки с первого скана и при пересканировании меняет в записи только уровень и немногие поля
(см. §12). Без описания остаётся
только пояснение. Всё в одну строку: Harbor склеивает переносы. Пояснение — до 300 символов. В тексте
перечисляются не больше трёх номеров Exploit-DB, остальные сводятся к «и ещё N». Для PoC указывается одна
ссылка, первая найденная, без схемы и «www.», не длиннее 80 символов. Числа — как в таблице grype: риск с
одним знаком после точки или «<0.1», EPSS в процентах с одним знаком (без «.0») или «<0.1%».

Главная причина:

| Правило | Текст |
|---|---|
| 1 | «есть в каталоге KEV с <самая ранняя dateAdded>», плюс «, используется вымогателями», если так отмечено в KEV |
| 2 | «пакет помечен как вредоносный (бюллетень GitHub о вредоносном пакете), проверьте, откуда он в образе» или «встроенный вредоносный код (CWE-506)» |
| 3 | «риск grype <R>, порог <уровня> от <T>», для Low — «ниже порога Medium», затем «(EPSS <E>%, критичность grype <S>)»; при пересчёте — «риск <R'> по максимальному EPSS бюллетеня (<CVE>, <E>%), grype показывает <R>; <порог> (критичность grype <S>)» |
| 4 | «EPSS нет, взята критичность grype <S>», при понижении — «, понижена до High: без EPSS и KEV Critical не ставим», для Negligible — «, в Harbor это Low»; без критичности — «EPSS нет, критичность grype неизвестна» |
| 5 | «есть эксплойт в Exploit-DB (<номера>)» или «есть PoC (<хост/путь>)», затем «, уязвимость доступна по сети, критичность grype <S>» либо «, но критичность grype <S>» (вектор сетевой, но критичность ниже High) либо «, но вектор атаки не сетевой» (локальный, из соседней сети или физический) либо «, но вектор атаки неизвестен», если у записи нет ни одного вектора CVSS; дополнительный факт «без эксплойта было бы <L> (риск grype <R>)», после пересчёта — «… (риск <R'> по максимальному EPSS, grype показывает <R>)», без EPSS — «… (EPSS нет)» |

Дополнительные факты идут в таком порядке: сначала эксплойт («есть эксплойт в Exploit-DB (…)», «есть PoC (…)»
или «эксплойтов не найдено»), затем «в KEV нет». Для правила 1 вместо «в KEV нет» пишется «риск grype <R>», а
отсутствие эксплойта не упоминается; если находка из KEV ещё и вредоносная (правило 2), первым фактом идёт
текст правила 2: реагировать на компрометацию пакета нужно иначе, чем на обычную уязвимость. У правила 2
дополнительных фактов нет.

Примеры:

- Critical: есть в каталоге KEV с 2021-12-10, используется вымогателями; есть эксплойт в Exploit-DB
  (50590, 50592, 51183); риск grype 100.0. — Apache Log4j2 JNDI features do not protect against…
- High: риск grype 49.3, порог High от 30 (EPSS 52.4%, критичность grype Critical); есть PoC
  (github.com/guiimoraes/CVE-2025-15467); в KEV нет. — Issue summary: …
- Medium: есть PoC (github.com/metadust/CVE-2025-11187), но критичность grype Medium; без эксплойта было бы Low
  (риск grype 2.9); в KEV нет. — Issue summary: …
- High: EPSS нет, взята критичность grype Critical, понижена до High: без EPSS и KEV Critical не ставим;
  эксплойтов не найдено; в KEV нет. — kin-openapi: ValidationHandler.Load() Fail-Open Authentication Bypass…
- Critical: есть в каталоге KEV с 2026-05-27, используется вымогателями; пакет помечен как вредоносный
  (бюллетень GitHub о вредоносном пакете), проверьте, откуда он в образе; риск grype 100.0. — Malware in
  @tanstack/…

## 7. Данные

- **База grype** обновляется как сейчас: ночной cron плюс ручной импорт архива на крайний случай.
- **Exploit-DB.** Скрипт `update-exploitdb.sh` в том же cron после обновления базы:
  1. качает файл по `SCANNER_EXPLOITDB_URL` через curl во временный файл; `HTTPS_PROXY` учитывается, если задан;
  2. проверяет, что в заголовке есть колонка `codes` и строк больше 10 000;
  3. атомарно заменяет старый файл.

  При ошибке старый файл остаётся, в лог пишется ошибка.
- **Копия в образе.** При сборке в образ кладётся копия файла. При старте, если в томе файла нет, она
  копируется туда, чтобы правило 5 работало до первого ночного обновления.
- **Отдельный том.** Файл живёт в своём томе `exploitdb`, а не в томе базы grype: при обновлении grype может
  чистить свой каталог.
- **Устаревшая копия.** Если загруженный список старше `SCANNER_EXPLOITDB_MAX_AGE`, в лог пишется
  предупреждение — при загрузке или позже, когда список устареет в работе (ночное обновление перестало
  работать); одно предупреждение на каждую версию файла. Сканирование продолжается.

## 8. Безопасность

- **Ключ API.** `SCANNER_API_KEY` обязателен: без него коннектор не стартует и пишет понятную ошибку.
  - На `/api/v1/*` ключ принимается в заголовке `Authorization: Bearer <ключ>` или
    `X-ScannerAdapter-API-Key: <ключ>` и сравнивается за постоянное время.
  - Без ключа или с неверным ключом — ответ 401.
  - `/probe/*` и `/metrics` открыты.
  - В Harbor при регистрации сканера выбирается авторизация Bearer или API Key.
- **Учётные данные реестра.**
  - Basic от Harbor — используются его логин и пароль.
  - Bearer или пусто — как в текущем образе, подставляется своя учётка `SCANNER_REGISTRY_USERNAME/PASSWORD`,
    но только если хост реестра есть в `SCANNER_REGISTRY_TRUSTED_HOSTS` и учётка задана.
  - Для остальных хостов подстановки нет: Bearer передаётся grype как токен, без учётных данных образ
    скачивается анонимно.
  - Рекомендуется учётка робота Harbor с правом pull, а не admin.
  - Жёстко прописанный в main `admin/Harbor12345` удаляется.
- **Логи.** Заголовок авторизации, пароли и токены в лог больше не пишутся, только тип авторизации. Сейчас
  main пишет их как есть.

## 9. Проверка

- **`pkg/policy`:**
  - каждое правило;
  - границы порогов по показанному риску: 9.94 и 9.96, 29.94 и 29.96, 69.94 и 69.96, а также ровно 10, 30, 70;
  - пересчёт по максимальному EPSS;
  - находка без EPSS;
  - вредоносный пакет по каждой из пяти формулировок GitHub, по формулировке RustSec, по списку бюллетеней с нестандартным заголовком
    (по GHSA и по CVE, только для бюллетеней GitHub: запись дистрибутива с той же CVE не вредоносная) и по
    CWE-506; уязвимость со словом Malicious в середине или в начале другой фразы
    вредоносной не считается;
  - эксплойт при сетевом и локальном векторе, при разной критичности grype;
  - текст пояснения.
- **Множитель критичности** на реальных находках даёт тот же риск, что grype, с точностью 0.1.
- **`pkg/exploitdb`:** разбор файла, строки с несколькими CVE в `codes`, перечитывание после замены файла.
- **Сборка отчёта:** одна CVE в трёх пакетах даёт три строки с правильными пакетами; формат описания и ссылок.
- **API:** 401 без ключа и с неверным ключом, 200 с ключом, пробы доступны без ключа.
- **Реестр:** подстановки учётки для хоста вне `SCANNER_REGISTRY_TRUSTED_HOSTS` нет.
- **Живой прогон** на реальных JSON grype: образ n8n (пример из обсуждения), postgres:15.19-trixie, образ на
  Amazon Linux 2. Уровни и пояснения сверяются с ожидаемыми.

## 10. Выкатка

1. Новый образ ставится рядом со старым на другом порту и регистрируется в Harbor вторым сканером.
2. Отчёты проверяются на тестовом проекте, в том числе какие учётные данные присылает ваш Harbor.
3. Новый сканер становится сканером по умолчанию, запускается «Scan all». Старые отчёты сохраняют прежние
   уровни до пересканирования. После пересканирования строк в отчётах становится больше: пакеты с одной CVE
   больше не сливаются в одну строку (так во всех режимах).
4. Откат: вернуть старый сканер по умолчанию. Менять `SCANNER_RISK_MODE` на работающей регистрации не стоит:
   уровни обновятся, а пояснения останутся от прежнего режима (§12).
5. Смена порогов `SCANNER_POLICY_*` или режима — через новую регистрацию сканера и «Scan all». Адрес
   регистрации в Harbor уникален, поэтому второй раз тот же адрес зарегистрировать нельзя. Два пути:
   - зарегистрировать коннектор под другим адресом того же сервиса (второе DNS-имя или сетевой псевдоним,
     второй опубликованный порт), сделать его сканером по умолчанию, запустить «Scan all» и удалить старую
     регистрацию;
   - на время переключения сделать сканером по умолчанию другой сканер (например, Trivy), удалить регистрацию
     коннектора, зарегистрировать его заново по тому же адресу, сделать сканером по умолчанию и запустить
     «Scan all».

   При удалении регистрации Harbor удаляет и её записи о находках (внешний ключ с `ON DELETE CASCADE` в
   миграции `0050` Harbor 2.2, не менялся до 2.16).

## 11. Вне рамок

- Пробы с проверкой базы, политика вытеснения Redis, флаги `SCANNER_GRYPE_*`, которые grype не понимает,
  исправления `deploy.sh` — отдельной задачей.
- Уязвимости ядра в пакетах вроде kernel-debug-devel — через список исключений Harbor, а не правилами.
- Свои источники вредоносных пакетов помимо базы grype. Пакеты OpenSSF malicious-packages уже приходят через
  бюллетени GitHub («Malicious code in»).

## 12. Известные ограничения

- Harbor хранит запись о находке (CVE, пакет, версия) одну на регистрацию сканера. При повторных сканах
  Harbor 2.10–2.13 обновляет в ней только уровень, 2.14 и новее — уровень, версию с исправлением, оценку CVSS
  и статус (и только когда поменялись уровень или статус). Описание и ссылки остаются с первого скана
  (проверено по исходникам Harbor, `report_converters.go`). Поэтому пояснение —
  это оценка на дату в его начале: если уровень потом изменился (EPSS, KEV, новые эксплойты), текст этого не
  отражает, а новые ссылки на эксплойты не появятся. Свежие тексты даёт только новая регистрация сканера.
  Прежний коннектор, дописывавший расчёт риска в описание, был устроен так же.

- Шесть KEV в kernel-debug-devel получат Critical, хотя через контейнер ядро не атакуется.
- Шаблон PoC находит и безобидные примеры, которые просто роняют программу. Поэтому эксплойт даёт High только
  при сетевом векторе и критичности grype High или Critical.
- Для находки с одной CVE риск совпадает с grype. Для бюллетеней с несколькими CVE он пересчитывается, и в
  пояснении указаны оба числа.
- Вредоносные пакеты grype видит только по бюллетеням GitHub: npm, PyPI, RubyGems, NuGet, crates.io, Go, Maven,
  Packagist. Почти у всех нет ни CVE, ни EPSS, ни CVSS, и уровень им даёт правило 2.
- Список бюллетеней с нестандартным заголовком — снимок базы от 2026-09-15, а такие бюллетени продолжают
  выходить: 26 из 62 опубликованы в 2025–2026 годах (крейты RustSec правило 2 ловит по формулировке, остальные
  пишут авторы пакетов или PyPA — cline, mistralai, @cap-js/openapi, Telnyx, intercom, LiteLLM). Новый такой
  бюллетень правило 2 не узнает, пока его нет в списке: с CVE он пойдёт по лесенке и, скорее всего, получит
  Low, без CVE — критичность grype, не выше High. Список стоит обновлять раз в квартал: искать в базе grype
  бюллетени GitHub, у которых в заголовке или ссылках есть malware, backdoor, malicious, trojan, compromise,
  impersonat, typosquat, hijack, dropper, stealer или «unauthorized … publish», и вручную отбирать
  вредоносные пакеты. Бюллетень с совсем нейтральным заголовком и ссылками (как у event-stream) такой поиск
  может пропустить.
- Шаблон PoC смотрит на адрес, а не на содержимое. Копии бюллетеней и служебные страницы исключены (§4.2);
  остаются ложные срабатывания: репозитории с «poc» внутри слова (EspoCRM, Neo4j APOC), страницы, где слово
  metasploit встречается без эксплойта (заметки к выпускам Metasploit), и копии бюллетеней с нестандартным
  названием (одна такая в базе — `Apache-Struts-2.3.20-Security-Fixes.html`). Пропуски: gist без `#file-cve-…`
  в ссылке, PoC глубже корня репозитория, raw.githubusercontent.com и новый адрес Packet Storm
  `packetstorm.news/files/id/<n>/` (с 2025 года, 158 ссылок в базе, без названия в адресе — по нему не
  понять, эксплойт это или бюллетень).
- Факты бюллетеня с несколькими CVE сводятся вместе: эксплойт может быть у локальной CVE, а сетевой вектор — у
  другой, и правило 5 может поднять находку до High «по сети». По одним только ссылкам на PoC так устроены 273
  из 8 797 бюллетеней ALAS/ELSA с несколькими CVE (с номерами Exploit-DB — больше); у 242 из них критичность
  grype High или Critical, остальные поднимутся только до Medium. Пример — ALAS2-2018-1023. Точнее —
  сопоставлять эксплойт и вектор по каждой CVE; это доработка на будущее.
